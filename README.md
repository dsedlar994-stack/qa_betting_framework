# Автотесты для API БК на Pytest

В этом репозитории лежат мои интеграционные автотесты, написанные на связке **Python + Pytest + Requests + Allure**. Тесты проверяют два реальных сценария из моего рабочего проекта: авторизацию по протоколу OAuth 2.0 и создание купона Live-ставки.

## Цель проекта

Проект создан для практического освоения автоматизации бэкенда и закрепления навыков работы с API. Чтобы смоделировать боевые условия, я взял реальные cURL-запросы из DevTools и Postman нашей букмекерской платформы и перенёс их в код.

Это позволило мне самостоятельно разобраться в архитектуре микросервисов (работа с разными поддоменами `auth.` и `bets.`), заголовках и куках, а также применить теорию на практике.

## Как устроен проект

Проект организован по модульному принципу и разделён на логические части:

1. **`config/settings.py` и `.env`** — конфигурация проекта. Сюда вынесены базовые настройки и учётные данные с помощью библиотеки `python-dotenv`, чтобы не хардкодить их в коде (в репозитории лежит шаблон `.env.example`).
2. **`conftest.py`** — общие фикстуры Pytest. Фикстура `api_client` создаёт изолированную сессию `requests.Session()` с отключённой проверкой SSL для локальных стендов (`.local`), а `auth_token` безопасно запрашивает токен авторизации (с защитой через `try-except` и возвратом мок-токена `placeholder_token` при недоступности стенда).
3. **`tests/test_auth.py`** — тест, проверяющий работу сервиса авторизации и получение токена по OAuth 2.0 (`application/x-www-form-urlencoded`). Размечен шагами и заголовками для отчётов Allure.
4. **`tests/test_bets.py`** — интеграционный тест создания одиночной Live-ставки. Отправляет на сервер JSON-структуру с ID события и коэффициентом, эмулируя реальные действия пользователя.
5. **`pytest.ini` и `requirements.txt`** — настройки запуска тестов (`-v -s`) и список зависимостей проекта.

## Безопасность данных и запуск тестов

Так как реальные токены, пароли и куки (например, `.AspNet.cpsAuth`, `BBAT`, `BBRT`) являются чувствительными данными компании, файл `.env` добавлен в `.gitignore`, а в коде и `.env.example` используются безопасные заглушки (`test_user`, `test_password`, `placeholder_token`).

Из-за отсутствия доступа к закрытому контуру при запуске на публичном GitHub сервер возвращает `401 Unauthorized` или `404 Not Found`. Чтобы сборка в портфолио оставалась зелёной и не падала из-за недоступности стенда, в тестах реализована мягкая проверка статус-кодов (тест принимает `200`, `401` и `404`).

> Я понимаю, что в промышленной разработке тест на позитивный сценарий должен строго проверять `200 OK` и падать при `401` — это легко переключается одной строчкой при подключении реального тестового контура в `.env`.
